# 09:19 QQ 历史图片进入桌面上下文的排查与修复

日期：2026-10-13（Asia/Shanghai）。关联请求 `5fcdf846-8bef-4563-97d1-a163b8dea33f`。

## 核查结果

只读读取生产日志、ExperienceStream 与原有媒体文件，在内存 SQLite 快照中回退至 09:19:40 并重放 ContextBuilder。得到 **8 张图片、261,216 载荷字符**，与该次实际请求日志逐项合计一致。这 8 张全部是 Owner 在 QQ 群发过的近期历史图片，全部已转为 JPEG 缩略图，最大边长不超过 512px；没有原图直接重放，重放中没有本地图片。截图中的“本地 4 张 + 外部 4 张原图”不符合这次数据。

问题位于 cognitive_timeline 的跨渠道近期经验投影：Owner 的 QQ 群消息保留为 USER 角色并携带图片；桌面 ContextBuilder 随后压缩这些图片，但没有按当前聊天需求排除历史群图。因此“摸狗头”这种普通闲聊也自动带着 8 张群图。第三方群聊批次摘要和明确 read_social_context 图片回查是其他路径，本次没有执行图片回查工具。

32,617 是三次调用的 Token 总量，其中输入 31,552：Router 7,640，主 Agent 21,505，正文修复 2,407。主 Agent 的首次回复 JSON 未通过协议校验，补回复成功。261,216 是图片 URL/base64 编码载荷的字符数，不是图片 Token；接口的 image_tokens 明细实际报告 0，不能用载荷÷4或报告值 0 推断整条图片处理链的成本。Router 本身的输入及系统/时间线文本也需要计入总量，本次不更改用户工具强制暴露配置。

## 修复

共享 cognitive_timeline 在输出目标为 Desktop/Web 时，不自动携带 QQ 群历史消息的图片像素，保留文字、来源、Timeline Unit 原文引用及“曾附图”摘要，并提示模型按需使用 read_social_context 回查视觉细节。相同规则覆盖普通 Agent、Planner 的历史上下文和 FAST，不改原事件、附件、媒体缓存或历史消息存储。

当前触发消息的实际新图在独立投影中保留；明确引用图片与 read_social_context 已请求的图片结果继续进入模型。QQ 输出目标、QQ 私聊历史、本地历史图片的既有规则保留。统计界面将已知图片 Token 明确标为“接口报告”，数值 0 继续保留，缺少数据仍显示未返回。

同一内存快照修复后重放：自动携带群图 **8 → 0 张**，图片载荷 **261,216 → 0 字符**，8 条附图摘要和来源保留。这个结果证明发送载荷变化，不证明实际生产 Token 节省。
