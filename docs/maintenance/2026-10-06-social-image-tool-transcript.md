# 群图回查后 HTTP 400 与连续重试失败

日期：2026-10-06。依据用户 10:53 对话截图，检查日志并修复同一请求在工具完成后的模型消息结构。没有调用真实模型、重跑正式工具、发送外部消息或重启正式实例。

## 日志证据与判断

| 时间 | 请求 | 结果 |
| --- | --- | --- |
| 10:54:24 | `d889c023-6754-410f-880e-d912636928f0` | 两次 `read_social_context` 已成功；后续模型返回 HTTP 400 |
| 10:56:05 | `afcb747c-d799-48b7-a95d-42fd20d11c36` | 仅重新生成回复，仍为 HTTP 400 |
| 10:56:26 | `75ef4003-a489-4b89-8c22-1ace3fa5b6bb` | 再次仅生成回复，仍为 HTTP 400 |

三次均记录 `invalid_request_error`、`retryable=False`，模型为 `deepseek/deepseek-v4-flash`。首次工具执行前的模型请求已成功；工具执行后模型输入图片数为 5，两次重试均为 6。这不是日志中的超时或工具权限拒绝。

失败请求的尾部结构为：`assistant(tool_calls ×2) → tool(1) → user(历史图片) → tool(2) → user(历史图片)`。工具调用 ID 均能对应结果，旧日志的 `unmatched_tool_results=0` 只验证数量与归属，未检查消息连续性。原生工具调用要求批次结果连续返回，图片观察不能插在尚未结束的工具结果之间。

`core/agent.py` 在每次 `read_social_context` 成功后立即把 `SocialTraceReader.image_messages()` 添加到对话，造成同一批次两次回查的结果被图片消息隔开。回复重新生成保留工具历史，因此重放同一错误结构，稳定出现 400。旧错误记录没有保存上游错误正文；这里基于实际角色序列和源码确定存在协议错误，正式模型恢复仍需加载修复后验证。

重复提醒是另一处本地问题：仅补回复的模型仍失败时，降级函数把旧的降级回复作为草稿，再附加同一提醒。截图中三条相同提醒即来自连续拼接。

## 修复

`models/openai_compatible.py` 在发送前调整完整的原生工具结果批次：先返回全部已存在的结果，再附上回查图片。只允许移动有 `social-image:` ID、图片载荷及 `image_timeline_scope=attention` 的历史图片观察；真实用户输入、缺失结果、重复结果导致的不完整批次均不猜测修复。文本工具协议沿用原有转换。

顺序调整仅作用于出站消息视图，不修改正式对话，不删除图片、不丢失来源标记、不伪造工具结果；推理字段仍附在对应 assistant 调用上。旧失败历史也在发送时被调整，无须重复已完成的业务工具。

`core/agent.py` 降级回复在附加提醒前删除草稿中的同一条提醒，保留已有状态文字，连续失败也只显示一次。

## 验收与边界

- Provider、Agent、Gateway 与群聊历史专项最终 **101 项通过**。模拟 HTTP 服务严格检查原生工具批次连续性；真实的 SocialTrace 图片回查流程执行两次读取后正常生成回复。
- 同一份旧交错历史连续发送三次均通过模拟服务校验；调用 ID、图片、推理字段保留，调用者对话未修改。
- 真实用户插入、结果缺失与重复结果不被移动或补造；三次补回复失败保留两条已完成工具结果且提醒恰好一次。
- 一次中间测试夹具缺少已执行工具状态，另一处使用了不存在的接口参数，修正后专项通过；没有将中间失败当作最终验收。
- 顺带验证前次根目录清理后的冷启动：pytest 的新临时目录位于缓存内部，但 pytest 在建立夹具时尚未创建缓存父目录。根 `conftest.py` 增加启动阶段创建共享父目录的逻辑；清空缓存后测试通过，根目录只出现一个 `.pytest_cache/`。
- `git diff --check` 通过。未做真实模型联网复验，未自动修改正式运行实例。

生效需从托盘完全退出朝汐后重新启动，再使用原回复的重新生成按钮。进程内“重启 Core”不能重新加载 Provider 源码。这里解决请求结构，不保证其他独立的上游 HTTP 400 原因也自动消失。
