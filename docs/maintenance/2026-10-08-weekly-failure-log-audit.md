## 统计口径与证据

- 日志来源只有 `.zhaoxi/logs/zhaoxi.log` 及 `.1`—`.5`，轮转日志完整覆盖该窗口。扫描 193,641 条带时间戳记录，其中 WARNING 10,140 条、ERROR 46 条。`.5` 用于确认覆盖范围，没有记录落入本次窗口。
- 前台以 `request_started` 和 `request_id` 去重，用 `runtime_finished` 及 Web 失败事件确认终态。一次重试是一个新请求；该分母不包含后台活动或所有 QQ 调用。
- Beat 按 `id` 去重并取最后状态；正常静默、门控跳过不算失败。
- 后台缺少请求关联 ID 的日志只能统计失败尝试或错误记录，不能把记录数当作受影响用户数、任务数或 bug 数。不同分类可能描述同一次失败，不能相加。
- 排除测试目录、诊断数据库副本；结构元数据用 `ast.literal_eval` / `json.loads` 解析，不执行日志内容。证据未复制用户聊天正文、图片或密钥。
- 一周内混有多个代码和配置状态，日志没有逐条构建版本。历史出现过的问题不等于当前版本仍未修复；“成功终态”也不保证自然语言回复或业务效果完全正确。

[结构化证据](evidence/2026-10-08-weekly-failure-log-audit.json) 保存日志文件大小、SHA-256、时间范围、失败请求 ID、时间与行号、分类统计及隔离复现结果。活跃日志仍会增长和轮转，哈希仅对应审计读取时的文件快照。

## Bug 与可疑问题清单

### B01 · P1 · 已确认：后台 6,000 Token 预算与输入不匹配

[内部活动执行](../../src/zhaoxi/internal_activity/runtime.py) 的 `provider_budget_scope(needs.get("llm", 0), 6000)` 固定为 6,000；[摘要认知](../../src/zhaoxi/perception/runtime.py) 同时调用通用 ContextBuilder 构建上下文。Web 的前台 Token 调试预算不会直接改变这里的硬编码额度。

在 3,161 次上限为 6,000 的超限记录中，**3,131 次仅输入就超过 6,000**；输入中位数 7,386，最大 25,420。当前 [预算实现](../../src/zhaoxi/reliability/retry.py) 还会根据返回 usage 检查额度，导致已经完成的模型调用因超限被拒绝。该组调用报告的总 Token 合计 26,761,720；它包含重复输入及可能的缓存用量，**不是账单收费 Token 或成本估算**。

代表证据：10-02 22:08:24，`zhaoxi.log.4:10411` 预算超限，紧接 `:10412` 摘要认知失败、`:10413` 无变化。

建议：按活动定义预算，并在调用前约束输入上下文和输出预留；让摘要活动使用其所需证据，避免仅抬高全部活动预算后继续发送同样膨胀的上下文。

### B02 · P1 · 已确认：摘要处理失败变成 NO_CHANGE，堵住最旧任务

`process_pending_snapshot()` 捕获异常后返回 `0`；[perception 活动适配器](../../src/zhaoxi/internal_activity/activities/legacy.py) 把它映射为 `NO_CHANGE`。内部活动成功路径随即清空 `failure_count`、更新成功时间，因此失败退避无法生效。[摘要队列](../../src/zhaoxi/perception/store.py) 又总是取最旧的 PENDING 项，失败项不会推进或隔离。

全部 **3,468 次摘要失败后 2 秒内均出现 perception_cognition 的 ACTIVITY_NOOP**。这是失败状态吞掉的直接日志证据；并非 3,468 个不同摘要。

10-08 23:44 的 SQLite 只读采样：**PENDING 281、PROCESSED 144**；最旧待处理摘要 `abec282d8eb2414eb683f07fe89de698` 的窗口结束时间是 **10-03 12:57:47**。这是当前数据库快照，包含窗口外数据，不作为本周新增任务数。

建议：区分“没有待处理项”“成功无变化”“处理失败”，向活动调度器传播失败；保存重试次数、下次重试时间，超过次数后保留证据并暂时隔离失败项，让后续摘要继续处理。

### B03 · P1 · 当前代码已复现：空内容消息令待整理计数 TypeError

[InternalActivityRuntime._pending_turns](../../src/zhaoxi/internal_activity/runtime.py) 第 187 行附近：

```python
sum(e.actor_role == "OWNER" and e.content and
    e.event_type.value in {"USER_MESSAGE", "EXTERNAL_MESSAGE"}
    for e in stream.events_after(marker, limit=200))
```

Owner 消息的 `content=""` 时，`and` 表达式返回空字符串，`sum` 执行整数加字符串而抛出 TypeError。仅提取当前实际方法、用假的事件对象隔离调用，已复现 `unsupported operand type(s) for +: 'int' and 'str'`，没有初始化应用或写数据库。

日志有 **33 次 current_cognition_consolidation / candidate_check 的 TypeError**。日志未保存完整栈，不能证明每次都来自此行；但当前代码和隔离输入已确认存在该 bug。纯图片消息允许空文本后也必须正常处理，不能重新塞占位句来规避。

建议：计数使用布尔谓词或过滤后计数；同时明确纯图片是否属于应整理的有效互动。

### B04 · P2 · 已确认：失败请求的指标仍显示 completed

[ActionTrace](../../src/zhaoxi/observability.py) 的 `result_status` 默认值为 `completed`；[Gateway 异常分支](../../src/zhaoxi/interfaces/gateway.py) 设置 `response_status` 和终态，但没有同步更新该指标。全部 40 个前台终态失败请求均出现该矛盾。

代表证据：请求 `85652356-518e-4bb9-9b81-c3298045b6f8`，10-08 22:43:38，`zhaoxi.log:78` 指标 completed，`:80` Web 失败。

建议：以明确的任务状态和回复状态推导整体指标，并输出这两个状态。工具已完成而回复失败时保留“操作完成、交付失败”的区别，避免丢失已执行结果。

### B05 · P1 · 高优先级待查：空回复及回复 / 工具协议不稳定

25 个前台终态失败由空回复 / 无效主回复协议引起，另有 10 条工具参数协议损坏。10-08 22:21 的截断 JSON、22:43 的无效 JSON 说明本周末端仍有协议失败信号；但日志只记录结构特征，无法确定是模型没有遵循协议、流式拼接、截断还是解析器不兼容。

`provider_protocol_error` 的 3 个前台失败中，10-07 21:59:26 一例明确对应 `tool_arguments_invalid transport=text`；其余不能只凭 ProviderError 确定原因。2 个 `agent_loop_error` 也保留为未细分，调用耗时长不等于已证明超时根因。

此前已有裸工具 JSON / 混合回复协议修复；历史日志不能用来证明补丁未加载或当前补丁失效。后续需在当前构建下复核。

建议：增加不包含正文的诊断（finish_reason、结构类型、必需字段缺失、流结束状态），针对回复协议做有界的回复修复；避免重放已经完成的业务工具，也不要放宽防护而再次将 JSON 原文交付用户。

### B06 · P1 · 已确认配置故障；防护待完善：unsupported_model 持续失败

**208 次 HTTP 400 明确返回 `unsupported_model`，模型字段为 `deepseek-flash`**，集中在 **10-07 22:17:31 至 10-08 10:09:34**。5 个失败 Beat 的 HTTP 400 也在此时段。其他 3 个 400 使用的是 `deepseek/deepseek-v4-flash`，不能混为模型名称问题。

当前源码中未找到 `deepseek-flash` 的硬编码；没有证据证明是程序自行改坏模型名。该时段的实际配置与接口不兼容已经确认；最后一个此类错误是 10-08 10:09，不能推断当前配置仍错误。

建议：配置保存 / 加载时检查 endpoint 与模型名称的兼容性，保留明确诊断；对 unsupported_model 等永久错误暂停反复后台调用，配置修正后恢复。检查失败不应使有效前台配置被自动覆盖。
