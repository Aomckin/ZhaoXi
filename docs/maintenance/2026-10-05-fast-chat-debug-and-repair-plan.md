## 已实现的开关

Desktop 侧边栏「常用调试」、Web Dashboard 的设置与运行页嵌入的工程调试面板，都增加以下选项。共用 `/api/settings/interface`，保存到已有界面设置文件，通过 SSE 同步；重新加载和 Core 启动时恢复。

| 开关 | 默认 | 行为与边界 |
| --- | --- | --- |
| 允许多轮模型调用 | 关闭 | STANDARD 循环的模型轮数上限使用 `max_agent_steps`（默认 8），其中最后一轮仍保留给收口。总步数、模型调用与 Token 预算、工具轮数、失败修复、无进展和权限保护继续生效。关闭时保持普通 STANDARD 默认 3 轮、FAST 升级后 2 轮的既有行为。 |
| 强制使用非 FAST_CHAT（标准通道） | 关闭 | 主对话跳过 FAST Gate，Router 若仍选择 FAST_CHAT 则转为具备工具能力的标准执行入口；Owner 外部私聊同样禁止 FAST 分支。保留外部来源、频道、权限与写入边界。 |

强制 FAST_CHAT 与强制非 FAST_CHAT 互斥：单项 PATCH 开启其中一个会关闭另一个，同时请求开启两者返回 422。多轮开关独立。运行中的循环保持首次创建的安全额度，后续请求使用新设置。

临时排查可同时开启两个新选项，以绕开 FAST 的路由和过紧模型轮数；它们不会解决所有多阶段业务工具链，也不会让 FAST 自身拥有工具。FAST 升级后的业务工具轮数仍为 1，普通 STANDARD 仍默认 2，不能把调试绕行视为正式修复。

修改位置：`core/runtime.py`、`core/agent.py`、`cognitive/coordinator.py`、`perception/runtime.py`；Web schemas、设置 API、启动恢复、两份 HTML 与共享 `shell.js`。加载新代码需要重启 Core 一次；加载后开关即时保存，无需为每次切换重启。

第一处代码链路：`ZhaoxiAgent._safety_state()` 给 FAST 升级配置模型 2 轮、业务工具 1 轮、有效发现补偿 0 轮。`_run_loop()` 在 `begin_round()` 后再次检查 `model_limit_reached`，到最后一轮先清空工具 schema 并要求收口。因此第一轮若仅发现工具，第二轮就没有执行业务工具的机会。正常 STANDARD 的有效发现补偿机制存在，FAST 升级却没有继承。

第二处代码链路：`FastChatRuntime.validated_request()` 要求当前文本及 `trigger_span` 都满足 `current_evidence()` 的动作表达式。明确重试的短句缺少动作名，表达式判为无证据；失败操作的范围没有参与验证。不能仅靠增加几个泛化关键词解决，否则会让陈旧对话或引用内容误触发操作。

另有后台 Perception 多次输入约 8,183–8,350 Token 超过 6,000 快照预算的记录。这是独立预算问题，不是上述前台 FAST 工具冲突的原因。

## 可行修复方案

### 第一阶段：升级后继承完整标准执行额度

在 `_safety_state()` 取消 FAST 升级专用的 2/1/0 缩减，统一使用现有 STANDARD 配置：默认模型 3 轮、业务工具 2 轮、最多 1 轮有效发现补偿。FAST 草稿继续丢弃，升级保持单向，不返回 FAST；已经用掉的 FAST 模型调用继续记入整请求调用与 Token 预算。

这能容纳「发现工具 → 执行业务 → 回复」；配合有效发现补偿，可容纳「发现工具 → 读取 ID → 写入一次 → 回复」。无需引入第二套循环。总步数、总预算、重复失败锁定与无进展收口仍作为最后约束。应明确约定模型额度包含最终回复，避免后续继续按“可执行轮数”误配。

同步修正结果记录：若要求工具执行但没有任何业务操作，状态应记录为未执行/失败，并带明确原因；混合成功与失败记为部分完成。不能因为最终产生了文字就标记任务 `completed`，回复也应如实说明未执行。

### 第二阶段：让明确重试使用受限任务上下文

为上一轮未执行、或已确认安全可重试的失败保存最小上下文：任务/追踪 ID、Owner、session、频道、动作范围、执行结果和有效期限。当前消息明确要求重试且身份、会话、频道和动作范围一致时，把这一记录作为升级证据，引导 STANDARD 重新处理，并照常经过权限网关。

已成功执行、结果未知的写入、权限拒绝或取消不能自动重放；切换频道、主体或扩大动作范围时失效。不得把整段历史直接当成新增写入授权，也不得直接复用模型草稿里的工具参数。需要新确认的写入继续走已有确认流程。

### 回归与交付顺序

先实现第一阶段及真实结果状态，再实现第二阶段；调试开关保持默认关闭。至少覆盖以下行为：

- 默认模式下 FAST 升级后发现工具，再实际执行并回复；读取 ID 后写入仅一次。
- 明确重试能够衔接同一任务；陈旧、引用、否定、新频道/新主体和范围改变不能借用旧授权。
- 结果未知的写入不自动重试；权限拒绝、失败修复、重复发现、无进展和预算耗尽仍正常收口。
- 未执行与部分完成的日志、界面和最终回复一致；所有真实调用继续计入总预算。

真实模型验收先用隔离只读工具确认路由和调用顺序；写入场景使用临时夹具核验恰好一次，再按实际授权范围验收正式业务。当前补丁只实现开关，未宣称上述根因已修复。
