## 3. P0：统一 Visibility Contract，修复幽灵回复

### 3.1 已核实的原因

`core/agent.py` 将带业务 tool_calls 的 assistant content 放入内部对话；`interfaces/gateway.py::_new_output_messages` 在实时输出中过滤多数工具回合消息。`session/sqlite.py::save_sync` 却保存 assistant content，并排除 tool_calls 和 metadata。刷新后，原本用于判定内部消息的信息已经丢失，内部文本可能作为普通 assistant 消息恢复。

因此只改前端过滤不能解决问题，必须覆盖生成、持久化、恢复、模型上下文及认知摄取。

### 3.2 消息分类

| 类型 | 用户实时可见 | 持久化 / 恢复 | 模型上下文 | 自动记忆 / Current Cognition |
|---|---|---|---|---|
| internal_tool_turn | 否 | 内部 transcript 按现有存储边界处理；不进入用户历史 | 保留完整调用与结果配对 | 不当作助手对用户表达的事实 |
| interim | 是，不终结 turn | 独立 Runtime 事件；默认不进入历史 | 不进入普通对话上下文 | 不摄取 |
| final | 是 | 保存后历史可见 | 是 | 仅在实际产生正式回复后摄取 |
| permission / failure_notice | 按原用途可见 | 显式区分状态提示与正式答复 | 不冒充任务完成 | 不作为成功事实学习 |

采用一个持久化的消息类别 / 可见性字段以及统一判断函数，避免维护多组可能冲突的布尔值。用户消息、图片、表情、主动投递、外部平台消息的原有语义必须保留。

Web Live、Session Restore、QQ 输出及可重生成消息定位复用同一规则。带图片的 internal 消息也不能绕过过滤。过滤内部消息不意味着丢掉模型需要的 Tool transcript。

### 3.3 兼容与迁移

- 新字段必须穿过 SQLite 序列化与反序列化，重启后仍生效。
- 已存旧消息若丢失 tool_calls，不能仅凭文风或“我先……”猜测并批量删除；保留原记录，使用可验证来源标记迁移，无法判定者明确兼容处理。
- 增加“写入磁盘 → 新进程恢复 → 渲染”的测试，不能只测试内存过滤。
- 内部 Tool Observation 仍可走既有事实通道；禁止的是把内部 assistant 草稿误当作已表达的最终答复。

## 4. P0：最终回复先交付，后台维护后置

目标链路：生成完整 Final → 确认显式副作用结果 → 提交并持久化用户可见答复 → 返回给渠道 → 有序执行自动维护。

必需的会话持久化保留在交付前，测量其耗时。若持久化失败，定义明确错误语义，不能报告“已可靠保存”再静默丢历史。传输重复、刷新和断线重连按 request_id / message_id 去重，不重做写入。

AutoMemory、自动 Current Cognition 维护移到后处理。用户显式要求的 `remember_memory`、LifeHUD 写入及其必要确认保持同步。降级回复、权限提示不能一律作为正常成功 Final 喂给自动记忆。

统一覆盖 chat、权限批准后续执行、重新生成及适用的外部渠道，避免只优化主 chat 路径。

## 5. PostTurnMaintenanceQueue 的最低要求

优先复用现有任务管理、生命周期和存储设施；禁止把裸 `create_task` 当作可靠队列。

- 每个会话 FIFO；明确跨会话共享 Memory / Current Cognition 写入的串行或版本检查策略。
- 入队为冻结快照：request_id、session_id、trigger_event_id、用户和最终助手消息 ID/内容、渠道、时间、会话代次、结果状态；禁止稍后读取可变的“当前 conversation”。
- 队列有界；定义积压、重试上限、退避、失败可见性、停机排空和重启恢复。要求可靠执行的任务使用可恢复记录；禁止静默丢弃。
- 幂等键防止同一轮自动记忆重复写入；Current Cognition 更新使用顺序或版本保护，旧快照不能覆盖新状态。
- 新请求不等待上一轮整段维护，也不能被共享请求锁间接卡住；并发模型调用沿用全局限流，用户请求优先，不能因后台抢额度反而更慢。
- 清空会话或重置时撤销对应代次的积压任务，避免旧任务把已清空内容写回来。
- 维护失败不改变已交付答复；标记 maintenance failed，允许后续任务继续。
- 后台指标按原 request_id 保存，不能覆盖当前轮行动记录或更改当前输入框状态。

## 6. P0：Finalization Contract 与真实结果

最终回复必须独立成立，覆盖原请求主要事项和关键执行结果，明确未完成事项。内部草稿、中间回复均不代表用户已经收到了答案。不得只因之前产生过长草稿，就把正式回答缩成“好了”“记住了”。

不以最低字数校验；使用任务项和工具结果约束最终整理。简单请求仍允许简短回答。内部草稿可以作为待核验材料，不能直接拼接成最终答案，尤其是执行工具前的成功承诺。

工具结果已确认成功时，即使模型失败或超时，也必须交付明确的保留结果与未完成范围；不得自动重放写入。`task_status`、`response_status`、`maintenance_status` 分开显示：不能在最终回复失败后追加“本次任务全部完成”的误导性前端兜底。

为最终整理预留调用次数、tokens 和剩余时间；回归覆盖首次调用很慢、部分操作成功、权限恢复、最终工具参数错误等情况。超时策略先测清覆盖范围，不用延长硬超时掩盖循环。

## 7. P1：真实中间回复；取消定时心跳

保留 `emit_interim_reply` 独立事件能力，让 Agent / Planner 在有具体任务信息、后续还需执行时主动使用。内容应来自真实已知状态，不能提前宣告完成或未经授权的操作。

**禁止根据“已过 N 秒”自动生成聊天气泡，也不把同样固定文案迁移到 activity 里充数。** 输入框 activity 继续由真实事件更新。时间阈值若保留，仅用于防频繁发送，不是自动触发条件。删除旧稿的 Fallback Heartbeat 交付项与 `fallback_heartbeat_ms` 新增指标。

不额外调用一次模型只为生成“我还在想”。可将模型明确标记的进度通过独立事件提前交付；普通 tool-turn content 不能未经分类直接展示。保留次数限制、Planner 第二次须有新进展、失败后最终收尾。

没有可靠中间进展时允许没有气泡；验收重点是真实性和最终交付速度，不是每轮必须出现一次中间回复。

## 8. P1：抑制无进展的发现循环和上下文膨胀

09:50 的目录发现多轮耗时是本次新增的重点，不能只解决后台维护。

- 记录控制调用数量、动作类别、规范化参数指纹、发现结果版本/是否变化，避免记录原始私人内容。
- 相同请求内，对相同查询与相同目录版本复用结果；允许 need、组或目录版本变化后的合理查询。
- 识别连续无新能力、无新结果的发现循环，给模型明确一次收口提示，随后切换最终整理或明确说明缺失能力；不能无限消耗轮数。
- 工具发现缓存不能代替真实业务结果；权限改变或依赖变化后需失效。
- 暴露业务调用和控制调用各自次数、耗时；目前 tool_call_count 只看业务会掩盖发现开销。
- 对照每轮 system/schema/history/tool_result/image 体积，验证已有压缩是否生效；限制重复完整目录与已吸收的大工具结果，但保留任务所需事实及调用配对。
- 不在本补丁中盲目删历史或降低模型能力。输入规模和耗时的因果关系需用同一任务可复现对照支持。

## 9. P1：前端等待和可见状态

Final Reply 保留段落拆分。段间延迟由用户可见的“分段回复间隔”设置控制；设为 0 时立即完整显示。不得绕过该设置写死额外等待。浏览器完整渲染回执在最后一段实际显示后发送。

输入合并 debounce 单独计时、单独展示。本轮不静默改变用户现有合并设置；任务书验收同时报告点击发送 → dispatch 与 dispatch → final 的时间。

Planner 展示实际计划、步骤状态与耗时；普通 Agent 明确显示未启用 Planner。失败和权限等待有独立状态。后台维护单独展示，不让已交付的 turn 长期处于“进行中”。

## 10. P1：可信的时间测量

### 10.1 时间边界

- `request_received`、`final_reply_ready`、`response_sent` 是不同服务端事件。
- `final_reply_first_rendered`、`final_reply_fully_rendered` 由浏览器按 request_id/message_id 回执；没有回执显示“未知”，不能用 runtime_finished 代替。
- `ttfr_ms` 明确是否指中间回复或 Final；`semantic_interim_ms` 不再混入定时心跳。
- `post_turn_maintenance_ms` 独立，后台完成更新不能重写已记录的 Final 交付时刻。
- 浏览器与服务端时钟分开处理，不直接相减未经校准的 wall-clock；采用各端单调时间及事件关联，网络往返的估计必须标注。

### 10.2 阶段与调用

区分包容阶段与互斥区间：Planner、response_generation 可能包含模型和工具，禁止直接将两者相加。Other/Unclassified 用互斥区间或覆盖区间的并集计算，不能遗漏首轮 Agent 模型再归为“未知”。记录 routing、memory retrieval、context build、tool discovery、provider preparation/retry/backoff、business tool、session persist、conversation commit、response packaging、enqueue 等可定位区间。

每次 LLM 显示 owner、attempt、成功/失败/取消、输入输出 tokens 和 duration；每次工具显示业务/控制、步骤、等待权限与执行时长。自动维护整阶段与其模型子调用均可查看。补齐 failed / cancelled 结束事件，避免计时器漏闭合。

指标按 request 保存并区分前台快照与后台补充，避免上一轮完成事件串入新一轮。Debug 的汇总与侧栏使用同一指标契约。本轮实际使用的 Memory 候选必须随 request 快照展示最终分及 Text、Semantic、Graph、Time、Activation、Importance 等组成；展示不得触发第二次检索或 activation。

## 11. 验收场景与判定

| 场景 | 必须验证 |
|---|---|
| 模型返回 content + tool_calls | Live、刷新、SQLite 重启恢复、QQ 都不展示 internal；模型仍有配对 transcript |
| 主动中间回复 | 实时可见、不会终结 turn、不进入普通历史和认知；后续失败有最终收尾 |
| 慢模型不主动发中间回复 | 超过旧阈值也不出现 runtime_wait 气泡；不额外调用模型制造心跳 |
| LifeHUD + remember_memory | 必要写入同步完成；Final 覆盖两类结果；自动维护后置；不重复写入 |
| 模拟 AutoMemory 14s + Cognition 5s | Final 返回/展示不等待这 19s；可控本地测试中 ready 到 API 返回目标 < 1s，浏览器首显目标 < 1s（不含真实网络）；超标必须给对应持久化/渲染证据 |
| 下一轮立即输入 | 新一轮不等待前一轮维护；FIFO、快照与版本隔离正确；后台不抢当前界面 |
| 维护失败/重启/队列满/清空会话 | 答复不被撤销；任务失败可见、可恢复或明确撤销；无重复记忆和旧内容复活 |
| 重复目录查询 | 相同查询复用，无进展循环有界；不同查询仍可发现新工具；保留收口预算 |
| 工具成功后模型超时 | 显示操作结果与回复失败，不显示“全部完成”，重生成不重放写入 |
| 权限批准/拒绝、重新生成、外部渠道 | 与主 chat 共用可见性和交付规则；无权限等待误判成功 |
| 多段正式回复 | 按“分段回复间隔”逐段展示，设为 0 时立即完整展示；无绕过设置的隐藏 sleep；计入 fully_rendered 指标 |
| 耗时守恒 | 受控 fake clock 验证互斥时段不重计、首轮模型不落入 Other、失败取消可闭合、无浏览器回执不伪造交付 |

真实模型耗时有波动，不把总响应强行承诺到固定秒数。使用上述三轮类型的脱敏 fixture 做可重复验证，再进行用户同意范围内的真实模型只读验证；不得为测速重复写用户 LifeHUD 数据。

5. `web/static/index.html` 的 Final 展示、状态与交付回执。
6. `observability.py`、Provider、Planner 的时长契约及前后台快照。
7. 相关 Python / Node / 持久化重启 / 桌面或浏览器集成验证，更新开发记录并逐项给证据。

## 13. 不在本补丁中扩展的范围

不做 Planner 全面 UI、Current Cognition 内容重构、Memory Embedding 替换、Presence 2.0、视觉改版、FTS/ANN 重构。Router Fast Path 和供应商迁移另行评估。复用既有模块，避免为了观测改造业务架构。

## 14. 审阅后的完成标准

- 用户可见消息的规则在实时、历史、磁盘恢复、外部平台一致。
- 正式回复完整且先于自动维护交付，显式副作用结果可靠。
- 维护有序、有界、可诊断，旧轮不会污染新轮。
- 无定时中间气泡；真实中间回复保留，失败必有最终收尾。
- 重复发现循环受控，最终整理有预算，用户无需为同一操作反复催促。
- 用户能区分前台等待、模型执行、工具执行、后台维护、浏览器展示；指标不伪造交付、不重复累计。
- 原日志样本、可复现实验、实现改动和验收结果可以逐项对应。
