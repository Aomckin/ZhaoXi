# v1.4.5 本地文件工具排查（2026-10-03）

用户反馈给出 `docs/v1.4.x` 路径后，列出 v1.4.6 文档但未读正文，页面出现“模型生成的后续工具参数格式有误”。

## 运行证据

正式日志 `.zhaoxi/logs/zhaoxi.log`，请求 `5b49c944-7034-46a8-885f-8523e7024f19`，10:51:36–10:52:04：

1. 第一轮模型调用执行 `request_tool_group` 与 `inspect_tool_catalog`，只发现能力。
2. 第二轮 `mcp_filesystem_list_directory` 和 `mcp_filesystem_search_files` 均成功，分别约 24 ms、35 ms。
3. 第三轮触发 `forced_finalization`，原因 `round_limit`，工具 schema 已移除；没有执行正文读取。
4. 收尾请求 HTTP 200，但 Provider 解析失败，错误码 `provider_tool_arguments_invalid`；返回保留已执行结果的部分完成说明。

原日志没有保存协议错误细节，无法证明是 Windows 反斜杠转义、原生 JSON、文本 DSML 或其他具体语法错误。此次未推测或宽松修复未知参数。

## 已修复

- 工具能力继续由模型通过已有能力目录和 `request_tool_group` 选择，本次没有新增用户文本关键词匹配。
- 模型纯发现轮成功加载此前未携带的可用能力时，最多计入一次独立发现轮额度。默认最多四次模型请求：一次发现、两次业务工具执行、一次回复。仅查看目录、重复发现、失败发现、混合业务调用和业务开始后的发现都不增加额度；FAST 升级保持原有严格限制。
- 保持业务工具两轮、修复上限、`max_steps`、模型调用总预算、Token 预算和权限边界。实际模型请求仍全部计数；新增 `discovery_round` 指标与扩展原因。隔离文件验证“发现能力 → 列目录 → 读正文 → 回答”，覆盖不同措辞和不含领域词的请求。
- Provider 增加原生 JSON / 文本协议错误类型诊断，原生 JSON 记录行列位置，文本协议记录解析原因；不记录原始参数和私人文件内容。保留严格解析，不把损坏参数自动变成执行指令。
