## 修复

- 最终回复区分真实工具调用、FAST 内部升级与面向用户的正文。真实工具调用允许空 content，最终正文缺失或格式不完整抛出 `empty_model_reply` / `invalid_reply_protocol`，走现有错误提示与重试。
- 表情解析后也必须存在至少一段可显示内容；仅无匹配表情不再创建空消息。成功解析的纯表情仍有效。
- FAST 格式失败保留已接受的用户输入；网关可重试原消息，不制造第二条用户输入。失败不写选择历史、不进入回复成功后的维护队列。
- 决策历史在有可显示回复之后提交。有效正文遇到错误 / 截断 awareness 仍可交付，不追加修复模型调用；内部 JSON / XML 元数据不展示为台词。
- 最终回答压缩 `read_decision_context` 时，保留实际事实、原则依据 / 例外及引用；限定五个来源、每来源八条、字符串与数组长度，移除内部调试字段。不会修改持久化的原工具结果。
- 当前图片作为实际已提供的资料收据写入 Trace，不要求模型完整自报。收据证明资料已提供，不能证明模型确实据此推理。
- 行为协议先利用图片与前文，只查询改变结论的缺口；不凭“好好考虑”进入 FRAME，不重复查询同一 Memory。购买先判断要不要，再谈档位；不得臆造年费抵扣 / 升级优惠，也不得把回本门槛当成确定的使用年限。
- 调试接口和工程面板显示回复协议状态、正文长度及错误码，标明本轮交付失败与上次已完成的判断。常规日志只记录形状和长度，不加入模型原文或推理内容。
