# Zhaoxi v1.4.9 · Phase 3
## 统一回复运行时、98%+ 可靠性与技术债收口开发任务书

日期：2026-10-13。沿用原 Phase3 文件路径，替换原“先建立 Faculty Layer”的开发主线。

## 0. 目标与优先级

v1.4.x 要做到：真实日用端到端成功率稳定达到 98%+；能清的技术债清掉；重复、臃肿的设计退出。正常回复路径优化到足以替代 FAST，最终删除 FAST 独立运行时。

本 Phase 的交付重点是可靠性、正常路径性能和实现收敛。Decision / Memory 的 Faculty 语义用于按需提供上下文与记录回合状态，采用薄适配，不以搭建新框架作为完成标准。

优先级：

1. 先修正文失败、漏回复、重复执行、历史或反馈丢失等实际故障。
2. 再减少普通回复的常驻提示词、重复读取和不必要模型调用。
3. 正常路径实测达到要求后，删除 FAST 与重复分支。
4. 对剩余技术债逐项结案，不把“默认关闭”当作删除完成。

## 1. 98%+ 的验收口径

### 1.1 保障范围与分母

一个原始 request / source event 是一个请求。模型重试、回复补写、渠道重投递仍归同一请求，不能增加成功样本数。

保障范围包括：

- Desktop / Web 的有效用户请求进入入口后，从处理到页面交付的完整过程。
- QQ 在既有策略下应回复的定向消息，包括普通真人成员的有效 @ 和私聊。 eligibility 在资源门控和处理开始前记录；已符合条件却被内部路径漏掉的消息仍计失败。
- 已识别的工具行动、明确记忆请求、决策结果反馈等，需要核对实际结果或持久化回执。

无效输入、用户主动取消、按既有规则拒绝的 bot 互答、未要求自动回复的群聊环境消息单独记录，不混入成功率。不能事后把故障改名为“跳过”来缩小分母。服务或 Provider 故障造成的未交付仍计失败。

### 1.2 成功条件

端到端成功必须满足：在本次请求适用的时间与预算范围内，有有效正文或正确的当前阶段交付，且已知请求目标对应的结果可验证。

| 请求 | 必要证据 |
| --- | --- |
| 普通聊天 | 完整、可显示的自然正文与页面渲染确认；已发现的跑题或错误回应不能继续计成功 |
| 工具行动 | 所需动作的真实回执与正确的结果回复；模型声称完成不算回执 |
| 明确记忆、反馈保存 | 对应持久化成功结果；不能用自然回应代替保存 |
| QQ 定向回复 | 投递确认；不能只用模型返回或进入回复函数证明已发送 |
| 权限确认 | 正确交付确认提示可计回复阶段成功；业务任务仍为等待授权，不计业务完成 |

工具成功但正文失败、回复成功但必要保存失败是部分成功。通用兜底占位话、原始协议碎片、任务失败提示不能冒充目标完成。必要交付证据缺失时记为未证实，不静默按成功统计。

格式合法不等于语义正确。对漏操作、误绑反馈、错误事实等，结合真实回执、用户纠正与人工抽查核验；不增加一轮 LLM 裁判。

### 1.3 指标与目标

| 指标 | 目标与定义 |
| --- | --- |
| 端到端成功率 | 已验证成功请求 / 保障范围内已结束或到期请求，≥98%；未证实请求不得排除以提高比例 |
| 首次正文合格率 | 无需格式补写即可交付正文的请求占比，≥98%；升级或真实工具中间轮次不当作正文失败 |
| 普通闲聊调用次数 | 正常情况一次 Provider 请求；API 重试和补写都计入实际调用次数 |
| 普通回复端到端 P95 | 同模型路由、参数及相近输入/输出规模下，不慢于现有 FAST；记录实测数据 |
| 模型外前台开销 P95 | 先测基线，以 ≤500ms 为初始目标；网络等待与本地处理分开统计 |
| 普通闲聊输入 Token | 第一阶段目标：相对匹配的 FAST 基线减少至少 30%；不靠丢失必要事实或破坏人格达标 |
| 重复业务写入、越权、隐私串线 | 0 个已知未修复事件；单独作为发布阻断项 |

同时展示首次成功、恢复后成功、部分成功、失败、未证实及等待授权，不用一次合并比例掩盖恢复成本。

后台记忆形成、归纳、近期认知维护单独统计成功率、积压与恢复进度，不混入前台分母，也不能以聊天正常掩盖后台持续失败。

### 1.4 日用观察窗口

- 候选构建至少观察 7 天，累计至少 500 次真实保障范围请求；先验收有限窗口，不宣称它保证未来故障概率。
- 同时检查最近 500 次与该构建观察期整体结果，不挑一段最好看的窗口。
- 按 Desktop/Web、QQ 定向回复，以及闲聊、工具、图片、反馈/记忆请求分列；某类样本不足标“待验收”。总体 98% 不能替代关键路径核验。
- 记录实际运行的 Core 构建、前端资源版本、模型路由及影响行为的配置摘要。多个构建的数据不能混成当前版本成绩。
- 正常路径验证阶段还需登记“是否实际使用 FAST”；不能用旧 FAST 的成功结果证明新路径已经达标。
- 不为凑样本自动发送 QQ、重放业务写入或批量请求模型。没有实际样本就保留验收缺口。

## 2. 当前基线与必须保留的行为

当前源码有可复用基础：`run_direct()`、工具执行和渠道回复已经复用 `_run_loop()`；现有 Tool Domain Map、预挂载、slim finalization、图片释放、Provider 预算与失败用量统计继续使用。

近期真实故障包括：FAST 返回正常结束但不符合主回复协议，正文被拒绝后没有统一补写；管理页新旧脚本缓存混用导致入口空白。前者需统一恢复路径，后者需把完整入口与资源版本纳入页面核验。

Phase2 已落地的历史有源修复、`question_revision`、原文章节索引及来源状态校验保持兼容。剩余旧决策缺口不在本 Phase 猜测回填。记忆归纳已做预算内分批，但修后真实成功归纳仍需日用证据，不能随职责包装直接改成“已清债”。

不可回退的边界：

- QQ 普通真人成员定向回复策略保留；防 bot 互答规则不改。
- QQ 回复继续禁用 Planner；群聊不能接入 Owner 私人决策与记忆资料。
- 主动工作流与主动社交配置继续暂缓，本 Phase 不新增、启用或自动执行。
- 真实行动继续经过已有 Tool / Permission / Guard / Confirmation。未知投递结果不盲目重发，已成功写操作不因正文补写重放。
- Choice History、反馈、Journal、准则索引及 Memory 数据不删除；历史读取兼容不能作为死代码直接砍掉。

相关依据：[Phase2 计划书](Zhaoxi_v1.4.9_Phase2_日用清债计划书.md)、[有源修复记录](../maintenance/2026-10-13-p2-source-repair.md)。

## 3. 目标运行路径

```text
Desktop / Web / QQ 输入
    ↓
回合身份、来源、权限、引用与预算
    ↓
最小上下文
    ↓
统一 Agent Loop / 主模型调用
    ├─ 可交付回复 → 正文校验 → 统一交付 → 持久化与必要决策/反馈提交
    ├─ 需要资料或工具 → 按需挂载 → 真实执行与回执 → 继续同一 Loop
    └─ 缺有效正文 → 一次有界纯回复补写 → 重新校验；仍失败则明确失败
    ↓
现有队列处理后台记忆与近期认知
```

渠道适配器负责收发、身份、权限和投递确认；不各自维护一套回复生成、决策解析或恢复算法。统一不意味着把群聊与 Owner 对话合并成同一份上下文。

正常路径只保留一份上下文组装、回复解析、能力请求校验、预算、工具结果处理和恢复规则。图片输入也走同一 Loop，图片本身不等于必须调用真实工具。

## 4. 普通路径默认轻量

### 4.1 基础上下文

默认仅加入：人格与表达、当前输入、有限相关近期对话、实际消息引用、必要来源说明与很薄的能力控制说明。

以下不常驻：完整 Decision Guidance、近期待反馈选择列表、全量原则/日记/历史、无关长期记忆、完整 Tool Domain Map、工具详细 Schema、Planner 状态及与当前问题无关的活动信息。

Tool Schemas 根据实际需要挂载。图片保留现有缩略图预算和提取后释放机制；工具成功后继续执行已有上下文收口，不能因 Faculty 激活重新背回整套行动上下文。

### 4.2 Router 与预挂载

Router 不再是普通闲聊的必经前置调用。已有明确来源或资源线索可提供预挂载提示；不确定时由主模型在同一次生成中回应或请求补充能力。

保留现有 `RouteDecision.route`、`preload_tool_groups` 及真实可用域校验，避免另造 `lane / tool_groups / needs_planner` 的平行路由结构。Router 仅在确实有准备价值的路径使用，不替主模型决定 PICK / ADVISE / FRAME。

所有入口，包括确定性分流、图片、工具重试和 QQ，汇入同一回合状态与能力准备步骤；不能只在 Router 返回 `faculty_hints` 时才激活 Decision。

预挂载不是授权。Planner 仅用于确实需要的多步任务，不能成为普通回复的额外检查门。

### 4.3 激活准确性与控制成本

不再把“未激活 Decision 时，任何识别说明与字段字数绝对为 0”作为可靠性指标。允许少量共同控制说明；完整规则、资料和结构化记录按需提供。

原生提示只能帮助准备上下文，不能因关键词强制判决策。没有预激活时，主模型仍可请求资料或提供合法的必要决策信息；Runtime 校验后在本轮使用，不能静默丢掉真实选择或反馈。

允许确实缺资料的请求增加必要轮次，不为普通聊天新增固定分类调用。

## 5. 统一回复与控制协议

### 5.1 普通正文

普通回复的标准形式：

```json
{"reply":"自然回复"}
```

保留一个正文解析入口。可复用已有 `ReplyRepair` 与正文校验逻辑，先明确普通、控制和决策回包的条件，不新增多套解析器。

- 正文完整且有效，才能交付。
- 无 `awareness` 的普通回复不判失败，不要求输出 `NONE` 占位。
- 有效正文与可选 Sidecar 的解析、提交错误分开记录。
- 缺正文、空正文、截断协议或仅有配置回显不当作回复。
- 正常图片/表情表达继续经过现有表达解析；内部字段不显示到聊天。

### 5.2 能力请求与升级

统一一种控制回包。第一版优先复用可选 `escalation` 字段，由 Runtime 解释；删除与其并行的 `[escalate:{...}]` 输出要求，不使用 XML 或隐藏思考作为新传输通道。

```json
{
  "reply":"",
  "escalation":{
    "kind":"recall",
    "reason":"需要查本轮明确询问的旧事实",
    "trigger_span":"本轮用户消息中的连续原文"
  }
}
```

空正文只有在控制请求本身合法且被 Runtime 接受时才表示继续处理；空正文与空控制仍是失败。控制字段不属于 Decision Sidecar，普通、决策和工具路径共享相同校验。

迁移期可以受控读取已有旧格式，模型只收到一种新输出要求；移除 FAST 时删除不再需要的旧协议分支。

### 5.3 统一失败恢复

- 有效正文、可选元数据异常：保留正文，记录元数据异常，不为遥测问题再调用模型。
- 用户明确需要的决策登记、反馈或记忆保存失败：正文可交付，但任务记录为部分成功/失败，不能伪报保存完成。
- 无有效正文：最多一次纯回复补写，复用已确认事实和行动回执，不开放业务写工具。
- 补写共享本请求剩余 Token、调用次数与总时间，不申请新预算，不重放已成功动作。
- Provider 传输重试与正文补写分别计数，但由同一请求预算约束，不形成层层嵌套的无限重试。
- 补写仍失败时明确报告；不以通用占位回复改写为成功。

性能指标统计包含实际重试、隐藏思考报告用量与补写成本。新增固定 Faculty/分类调用为 0；失败恢复和必要资料轮次单独展示，不以“调用次数绝对不增”阻止有界恢复。

## 6. Decision：薄适配与完整闭环

### 6.1 复用现有实现

继续使用 `DecisionAwareness`、`DecisionAwarenessTrace`、`question_issue`、Choice History、Principles、Journal、Feedback 与 Reflection，不复制新系统，不重写存储格式。

激活时提供相应 Guidance；普通聊天不附完整提示词或候选历史。低价值 PICK 不预读整套资料；ADVISE / FRAME 只补会影响结论的事实。

保留服务对象，用显式回合激活状态控制注入与提交。不能通过把 `ContextBuilder.decision_awareness` 置空来切换：现有代码会由此开启旧日程快照或改变近期认知读取，造成上下文反弹。

### 6.2 最小 Sidecar

第一版沿用可选 `awareness` wire field，内部归 Decision 回合状态。未发生决策、反馈或回访时省略；无需为了换名称同时改所有解析和提交接口。

```json
{
  "reply":"今晚吃米粉吧。",
  "awareness":{
    "mode":"PICK",
    "decision_kind":"NEW",
    "decision_question":"在今晚米粉和泡面的晚餐选项之间作出选择。",
    "agent_recommendation":"米粉"
  }
}
```

| 信息 | 责任 |
| --- | --- |
| mode、decision_kind | 模型给出，Runtime 校验；不由 Router 强制定级 |
| decision_question | NEW 时模型抽象成自足问题；Runtime 用现有校验拒绝照抄原话、建议冒充问题等情况 |
| agent_recommendation | 真正提供建议时填写；predicted_user_choice 按需保留 |
| feedback、回访信息 | 明确承接已有选择时填写，核对实际候选 ID；不明对象不猜 |
| context refs、principle/journal IDs | 以本轮实际读取结果和回执核验，不接受虚构使用依据 |
| decision_id、timestamp、scope | Runtime 从真实回合生成 |

不能把 `decision_kind` 与 `decision_question` 从最小契约中删掉，否则现有准入会拒绝新记录。也不能由 Runtime 凭原话或建议编造抽象问题来补字段。

正文、Sidecar 校验、记录提交分开。只提交对应已接受结果的本轮记录，保证补写、过程回复、重生成和投递重试不会重复新增同一选择或反馈；幂等依据使用真实源事件/请求身份。

历史、待反馈选择与回访候选按需读取。真实反馈可以有 `mode=NONE`，不能因没有新决策而跳过反馈保存。

## 7. Memory：保留能力，去掉重复工作

前台 Recall 与后台 Formation 分开管理：

- Recall 使用现有本地 Retriever。近期对话足够时不查长期库；显式精确查询与 Memory 管理 Tools 保留。
- Decision 和 Memory 需要同一份资料时，复用本轮真实读取结果与 refs；相同查询避免重复检索和重复注入，不引入跨会话缓存。
- Formation 保持现有后台队列、来源事件、批处理、优先级、背压、重试与预算。前台未激活 Recall 不关闭 Formation。
- 明确“记住/忘记/修改记忆”继续按既有显式管理流程处理；自然事实优先由后台形成，不要求主模型为每件小事多跑工具轮次。
- 记忆归纳保留 Phase2 的完整记录分批、延期簇及真实失败成本统计。职责包装不能取消证据限制或提高预算。

本 Phase 不迁移 Memory 数据库，不改 Current Cognition 存储。私人记忆来源及 Owner 过滤继续在实际读取、形成与写入处执行。

## 8. 最小状态与错误边界

第一版仅需本轮状态、简单注册表及现有 Decision / Memory 服务的薄适配。复用当前 request / turn 作用域；共享 Manager 不保存跨请求的激活状态。出现实际重复职责后再抽 Protocol，不先造 Registry、Manager、Session 与完整生命周期框架。

本轮状态需能说明：能力是否启用、为什么激活、实际注入多少、用了哪些 refs、正文和元数据结果、提交或读取错误。

元数据或可选资料故障不拖死有效正文；必要事实读取失败时标明未核实，不靠降级编造高影响结论。异常限定到真实边界并保留原因，不用宽泛 catch 静默吞错。

内部历史、反馈和后台记忆的本地提交沿用现有授权、来源及持久化规则，不为这些原有操作新造 Tool。对外行动与现有显式管理 Tool 的权限流程保留；Faculty 不获取额外授权。

只设一个必要的迁移回滚开关：切换旧实现与新实现，作用范围明确。能力启停仍使用既有设置；不能把“关闭新层”误解释为停止决策学习或记忆形成。迁移完成后移除临时双实现及回滚分支，保留数据读取兼容。

## 9. 观测与成本

复用现有 Action Trace、请求身份、Provider usage、交付回执与管理页面，不另建一套观测系统。

至少可追踪：入口收到有效请求、实际模型尝试、协议校验、真实工具结果、回复就绪、页面渲染/QQ 投递、必要持久化、恢复与最终结果。缺环节显示未证实，并提供证据覆盖情况，不能只用 `HTTP 200` 或 `finish_reason=stop` 表示任务成功。

性能分开记录模型等待、本地上下文构建、检索、工具、补写、持久化和页面交付。阶段时间如果重叠要明确，不能把同一段等待累加两次。

保留现有八类：`System / Persona / Tool Schemas / Timeline / Tool Results / Images / Memory / Cognition`。Faculty 先作为来源明细展示；Decision 已计入 System、Recall 已计入 Memory 的内容不能再累加一次。以后改独立分类时同步从原分类扣除。

- 文本字符估算与 API 实际 Token 分开。
- Provider 未报告的图片或其他用量显示未知，不填 0 冒充实测。
- DeepSeek 当前只启用 JSON 对象模式，不能把未实际发送的完整 Schema 当作已节省 Token。
- 更新面板模块时维持统一资源版本和缓存校验，验收完整入口，不只直接导入单个模块。

## 11. 清债账本与删除要求

每项技术债记录：编号、真实现象/来源请求、根因和相关模块、影响、最小修改、验收证据、状态与剩余风险。

清理顺序：

1. P0：正文和交付失败、QQ 漏回复、重复写入、资料隔离、历史与必要反馈丢失。
2. P1：常驻 Decision 和完整能力目录、重复检索/注入、无价值路由调用、重复预算或恢复。
3. P2：替代完成后的 FAST、旧协议、重复入口、无调用者的配置与死分支。

删除前查实际调用者、配置与 UI/CLI 接线、存量数据读取依赖。保留身份、权限、持久化和必要兼容；不以删行数衡量清债。旧演示或闲置功能不能因“清债”被自动启用。
