## V148-01 · P1 · Internal Activity 不够会处理“我这轮什么都不该做”

**状态：用户已报告、截图可见；重复跳过写入历史的路径已只读定位，其他根因待验证。**

Internal Activity 现在“会调度”，但还不够会处理“我这轮什么都不该做”。无事可做、暂时不能做或主动选择安静，都应是正常结果；不应靠反复制造活动卡片表现系统仍在工作。

### 已观察到的现象

用户提供的 Dashboard 截图（2026-10-09）：

- 22:39:54 与 22:40:26 两轮，均出现“跑去群里晃悠了”“围观群聊中”“在翻旧日记”三条已跳过记录；理由均为“优先处理待完成的维护任务”，耗时为 0 毫秒，未发送外部消息。两轮相隔约 32 秒，重复的门控结果占据活动列表。
- 22:45:28，“想想要不要找你”显示“已完成 / 活动已完成”，耗时 14,962 毫秒，标记为轻量模型任务、未发送外部消息。折叠的技术详情不可见，截图无法判断实际模型调用数、业务变化或内部投递结果。

“未发送外部消息”本身不是 bug，也不等于没有用户投递或内部变化；15 秒耗时不能单独证明无效调用。截图同样不能证明维护债已卡死或前台遭到阻塞。

### 当前源码定位

| 位置 | 只读确认的行为 | 后续核对点 |
| --- | --- | --- |
| [Runtime](../../src/zhaoxi/internal_activity/runtime.py) `run_tick` / `_skip` | 启用的高优先级活动 dirty 标记可形成维护债；候选检查阶段抑制普通自动跳过回执，但进入调度选择后恢复记录，maintenance_pending 等跳过会写活动历史 | 同一理由、同一债状态的自动跳过是否应聚合；待处理、退避、不可执行、隔离状态是否准确区分 |
| [Scheduler](../../src/zhaoxi/internal_activity/scheduler.py) `select_registered` | 维护债或高优先级候选会阻挡 LEISURE / SOCIAL；同轮 debt 判断用于候选遍历 | 债是否真实可执行，何时重新判断；维护优先与长期饥饿之间的边界 |
| [回执](../../src/zhaoxi/internal_activity/receipt.py) `build_receipt` | 已有 NO_CHANGE；NO_MESSAGE 映射为 NO_CHANGE；changed 或 message_sent 可映射为 SUCCESS | 已完成、无变化、未发言和没有工作是否表达实际效果，避免泛化“活动已完成”掩盖决策结果 |
| [主动活动适配器](../../src/zhaoxi/internal_activity/activities/legacy.py) `proactive_due` / `proactive` | 已有候选检查与空投递返回路径；Runtime 对空列表记 NO_MESSAGE | 实际是哪种候选触发截图中的执行，是否有应在调用前排除的条件 |

因此，本问题不是“完全没有 no-op 状态”，而是候选、维护债、资源消耗、终态回执与日常展示还需要形成一致的安静收口语义。维护债持续存在的原因、无效模型调用和调度饥饿目前只是待验证方向。

### 期望行为与验收条件

- 无候选、无到期工作且无必要判断时，本轮自然结束；不调用模型、不制造业务变化。必要的内部时钟或诊断更新可以保留。
- 本地可确定的 Presence、冷却、预算、维护阻挡等条件在执行前判断；同一自动跳过理由持续不变时，日用列表不逐轮刷屏，技术诊断仍能追溯次数和最近时间。手动调试返回明确原因。
- 有真实候选、经过必要判断后选择不发言，是合法的安静结果；实际用量仍需记账，不伪装为零成本或业务更新。
- 无变化、成功更新、主动静默、失败、取消分别有准确终态；失败不能被吞成 NO_CHANGE，未发外部消息不能自动被当成失败。
- 维护债优先保留；无可运行工作、退避中和隔离后的状态要可解释，不让失效 dirty 标记永久压住其他活动。队列、冷却、预算恢复后可继续调度。
- 隔离验收覆盖：空闲连续多轮、重复维护阻挡、退避 / 全部隔离、维护完成、必要判断后静默、异常与前台抢占，以及重启后的状态恢复。

## V148-02 · P1 · 决策判定过松，记录缺少可独立回顾的问题摘要

**状态：用户已报告、截图可见；原文截取入库已只读确认，误判的完整对话与模型输出待复核。**

### 已观察到的现象与影响

用户提供的决策列表截图中：

- “填表已经有对应的东西了，在线测评那不是投递时该做的事”（2026/10/09 14:40:56）被记为 ADVISE。用户在修正事实 / 建议，系统却继续将该轮作为决策登记。
- “可以的话，我打算之后一天投官网简历25到30个，每周投6天”（2026/10/09 14:39:48）也记为 ADVISE。此句可能承载真实的投递节奏选择；应结合上下文判断是否新增决策或承接同一问题，不能仅凭它与上一条都标为 ADVISE 就断言两条均误判。
- “咯，知道该干嘛吧”（2026/10/08 19:14:40）被记为 PICK，建议为“把记录补进 Life HUD”。标题只有承接句，离开对话后无法知道要补什么记录、当时到底在选择什么；用户指出此类非决策内容被纳入决策。

问题有两个相连的方面：真正选择与事实补充、纠正、普通执行指令的边界过松；即使是真实决策，单条用户原文也无法承担之后回顾、结果反馈和反思所需的问题上下文。这会污染选择历史，并使后续判断或学习缺少可靠依据。

### 当前源码定位

- [Awareness](../../src/zhaoxi/decision/awareness.py) 已提示“真正的选择”才使用决策模式、反思或闲聊无需机械拍板；但记录路径仍以 `trace.mode != NONE` 为入库条件。提示已有边界不等于实际判定稳定；截图不能定位究竟是哪一步促成误判。
- 同一文件生成记录时，`summary` 直接使用 `(user.content or "")[:160]`；[Choice History](../../src/zhaoxi/decision/history.py) 继续将这段摘要以最多 160 字保存。已确认这不是结合上下文抽象后的决策问题。
- [后台反思](../../src/zhaoxi/decision/learning.py) 使用记录中的 summary 检索相关选择 / 日记，并将摘要与建议等信息提供给反思。虽有 context_refs / context_sources，引用本身不能替代可独立理解的问题摘要。

### 期望行为与验收条件

- 登记前确认存在真实待选择的问题：选择对象、需要判断的方向或取舍须能从当前轮与相关上下文得到。普通闲聊、事实补充、对建议的纠正、已明确动作的执行指令，不因朝汐给出建议就自动成为新决策；不确定时允许 NONE。
- 承接、纠正、确认和结果反馈应识别与已有问题的关系；同一决策的后续消息不机械新增一条独立选择。确有新的取舍或条件变化时才按其含义记录。
- **先对决策问题作简单抽象，再记录**：用一两句自足的描述写清“在什么情境下，要决定什么”，保留影响判断的必要选项、目标或约束。标题 / 主摘要用该问题描述；建议和最终选择分别记录，不能用朝汐的建议冒充问题或用户决定。
- 摘要结合实际相关对话、图片和已读取事实消解“这个”“之后”“知道该干嘛吧”等指代；缺失条件标为未知，不编造细节，不复制整段聊天。可另保留用户原文及来源引用用于追溯，但原文不再是唯一问题记录。
- 示例：投递节奏问题可概括为“安排官网简历投递节奏：是否采用每天25–30个、每周6天的计划”；这只描述截图可读的计划，不推断额外目标。Life HUD 条目的具体对象无法从截图恢复，应回查真实上下文，不补造内容。
- 验收覆盖真实 PICK / ADVISE / FRAME 与闲聊、纠正、补充、执行指令的区别；多轮承接避免重复登记；隔一段时间只读记录仍能理解当初的决策问题。历史信息不足的记录标为上下文不足，不能凭猜测补齐或用于可靠学习。

## V148-03 · P1 · User Principles 准则摘要索引未正确同步失效来源

**状态：用户已报告、截图可见；原文件缺失和索引展示路径已只读确认。自动更新 / 清理机制的具体缺口待开发复核。**

### 已观察到的现象与影响

截图中，“不继续投递该岗位”和“长期、高影响、难以撤销或核心价值冲突的选择需要人工判断”等摘要仍显示“Owner 整理的索引 · 使用中”，引用 `data/archive/user/决策协议 v1.0.md` 的 `2/L0`、`2/L2`。同一卡片已提示“原始资料未找到，应重新关联当前用户资料”，但失效条目继续挂在使用中的摘要索引里。

用户明确指出该文件早已不存在；本轮对该路径执行只读存在性检查，结果为不存在。问题不限于报一句找不到原文，而是原始用户资料发生变化后，摘要索引的有效状态与日用展示没有同步收口。

### 当前源码定位与证据边界

- [准则 Store / Archive Provider](../../src/zhaoxi/decision/user_principles.py)：`source_status` 已区分 missing / changed / current；Store 从条目和修订事件投影恢复索引，检索按条目自身 `status == active` 筛选。
- [管理页接口](../../src/zhaoxi/web/decision_learning.py)：返回全部索引条目并附加 source_status，没有在该路径自动改变条目 active 状态。因此“来源缺失提示”与“条目仍使用中”可同时出现。
- [决策上下文](../../src/zhaoxi/decision/context.py) 及 [反思](../../src/zhaoxi/decision/learning.py) 已有仅使用 current 来源摘要的过滤。不能据此截图声称失效准则已经实际参与判断；应进一步检查所有消费入口与实际运行构建。

### 期望行为与验收条件

- 原始资料删除、移动或内容变化后，摘要索引及时重新核对来源；missing / changed 条目退出有效使用集合，展示为“来源失效 / 待更新”，不再同时标成“使用中”。
- 同步覆盖新增、修改和失效来源。自动摘要须基于当前可读取原文，保留来源与修订记录；摘要始终是索引，不能升级为用户原话或硬规则。
- 来源缺失时保留可追溯历史，避免静默删除人工条目；历史失效项可在相应视图查看，日常有效准则列表不长期挂着失效摘要。
- 文件移动或更名不能凭文件名相似自动绑定另一份资料；重新关联须有可靠依据，不能把旧摘录当作仍有效的原文。新资料产生的摘要不应被旧修订投影恢复为过时内容。
- 所有决策检索、反思和回顾入口一致排除失效来源作为当前准则；原文暂不可读时说明缺失，允许按已知事实继续判断，不依赖过时摘要兜底。
- 验收覆盖删除、移动、更名、原文修改、恢复、重启后投影，以及重新关联 / 更新摘要；验证有效集合、界面状态和实际模型上下文一致，不重复造项、不丢失审计历史。

- 若存储存在、API 存在而页面缺失，定位展示链路；若 API 已缺失，继续检查会话窗口、投递合并和存储；若模型输入独独缺失，检查上下文构建策略。数据库窗口不含消息也不立即等于所有持久化来源永久丢失。

- 若证实历史已经丢失，记录受影响范围和可恢复来源，不用朝汐回复猜造用户原话；遗留缺口应明确标记，避免后续决策与学习将其当完整证据。

## V148-05 · P1 · v1.4.0 长任务中间回复在实际使用中从未触发

**状态：用户明确报告“一次也没触发过”；现有能力与门控已只读定位，实际未触发的原因未确认。**

### 现象与影响

v1.4.0 开发的长任务中间回复，在用户截至本次反馈的实际使用中一次也未观察到。长任务仍缺少预期的中途自然回应，等待时难以判断任务是否有进展；该能力虽然存在于代码和自动测试中，其日用有效性尚未得到证明。

## V148-09 · P1 · 重新生成可能重复注入用户输入，误判实际发送次数

**状态：用户已报告、截图可见；只读日志确认首次失败及后续成功请求的图片计数由 2 增至 3，体验库对应时段只有 QQ / Desktop 两个匹配图片事件。具体重复投影尚需核对实际 Provider 消息。**

### 现象

2026/10/09 23:42，用户在 Desktop 发送哭泣老鼠图片；首次回复失败，重新生成后朝汐说“怎么同一只老鼠还发三遍”。用户明确说明实际上只有 Desktop 一遍、外部信息层 QQ 群聊一遍。重新生成是同一次输入的回复重试，不应被解释为用户又发了一遍。

模型台词不能单独证明后端重复发送，也可能是计数或来源理解错误；以下证据加强了重生成上下文膨胀的疑点，但不直接认定三张都是同一素材。

### 本轮只读证据

- `.zhaoxi/logs/zhaoxi.log:32474`：23:42:08.062 首次请求 `b1f10153-8b71-4a3d-8e42-926263726309` 开始；`:32506`、`:32508` 于 23:42:19 因 empty_model_reply 失败。
- `:32530`：23:42:51.261 后续请求 `a749d7cf-8575-4669-bdd5-14ad2f720c23` 开始；`:32553` 于 23:43:05 成功结束。时间与用户所述重生成相符，日志本身没有明确的原请求关联字段。
- 两请求的 context_measured（`:32484` / `:32540`）分别记录 image_count=2 / 3、image_payload_chars=6862 / 9821。图片计数是上下文总量，不能直接等同于同一图片的用户发送次数；没有逐张哈希，尚不能确认新增的第三张就是重复老鼠图。
- 以 SQLite mode=ro 查询 `.zhaoxi/experience.db`，限定 23:40–23:44 的 USER_MESSAGE / EXTERNAL_MESSAGE 图片事件：QQ 事件 `fd40d33900aa49c1acf4b175928cf2c9`（23:42:06）与 Desktop 事件 `1b2d842e4c7940c68ed915fd459dbf16`（23:42:08.032），均无文本、各 1 张图片；媒体引用对象经稳定序列化后 SHA-256 摘要前缀均为 `edb8630834df356e`。这证明两个记录引用相同媒体对象，不是对实际图片字节重新计算的哈希。
- 此查询没有发现第三个同时间段的用户图片事件；不排除更早素材或上下文其他来源，也不能因此直接定位第三张图片的生成位置。活跃日志行号与库状态对应本轮读取快照。

### 源码排查入口

- [Gateway regenerate](../../src/zhaoxi/interfaces/gateway.py)：普通重生成裁掉本地原用户消息及其后内容，再以原文字 / 图片调用 run_natural；模型运行结束后才恢复原用户 metadata。工具完成后的重生成则走 resume_current_turn，保留已执行操作。
- [Context Builder](../../src/zhaoxi/core/context.py)：合并 Experience 时间线、当前输入及本地尾部，依据 trigger / event 等身份关系去重；需检查重生成是否保持原输入身份，以及旧事件与重新创建的本地消息是否被同时投影为独立输入。
- [Desktop 入流](../../src/zhaoxi/cognitive_stream/ingress.py) 与 [时间线投影](../../src/zhaoxi/cognitive_stream/timeline.py)：核对 source_refs、turn_id、message_id、event_id 的关联和旧本地消息投影。体验库没有新增第三条事件，不等于最终 Prompt 没有第三份副本。

### 期望行为与验收条件

- 重生成关联原始输入事件 / 消息 ID，不作为新用户发送；允许新请求 ID，但输入来源、时间和语义身份保持一致。
- 原输入同时存在于 Experience、Conversation、当前触发和 Recent Experience 时，只呈现一次逻辑输入；按事件身份及投影关系去重，不仅按图片内容粗暴合并。QQ 与 Desktop 的两次真实发送须保留两条来源事实，不混成一次，也不把重试副本算成第三次。
- 对首次和重生成的实际模型消息，比较逐项来源、事件 ID、角色、图片索引及内容摘要；区分合法保留的其他图片与错误副本。诊断不额外记录图片正文或敏感 URL。
- 验收空回复后重试、普通回复重生成、工具完成后仅补回复、纯图片 / 多图、QQ 与 Desktop 同图、连续多次重生成、刷新 / 重启。检查用户事件不增长、当前输入不重复投影、模型不将重试解释成用户重复发送；业务工具不重放。
- 若消息与附件实际没有重复，转查模型对重复投影说明、渠道来源或台词次数的误读；最终归因以实际输入证据为准，不能用“发三遍”一句话替代验证。

## V148-11 · P2 · 记忆维护将正常跳过误报失败，真实失败原因被泛化

**状态：当前源码确认并以原方法隔离复现；自动候选通常有前置守卫，不能认定所有历史失败都是误报。**
