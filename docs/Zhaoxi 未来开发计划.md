# Zhaoxi 未来开发计划

> 当前状态：正式版骨架已经完成。  
> 本计划记录未来可能继续开发的长期方向，不代表近期立即启动，也暂不绑定具体版本号。

---

## 一、核心定位

Zhaoxi 的长期目标不是成为一个功能越来越多的聊天程序，而是逐渐成为：

> **跨设备存在、理解生活状态、能够实际行动，并自然融入日常环境的个人生活 Agent。**

未来所有开发方向都应围绕三个核心能力展开：

### Presence
朝汐能够持续“存在”在暗苟酱的生活环境中，而不是只有打开聊天窗口时才出现。

### Context
朝汐能够理解当前生活状态、历史记录以及正在发生的事情。

### Action
朝汐不仅能够给出建议，还能够调用 Tools 实际完成任务。

---

# 二、最高级架构原则：朝汐只能有一个

未来双端化必须遵守：

> **Single Active Presence**

即任意时刻只能存在一个真正活跃的朝汐实例。

电脑端和手机端不是两个朝汐，而只是朝汐可以暂时存在的两个载体。

```text
                Zhaoxi
                   │
          Active Presence
                   │
          ┌────────┴────────┐
          │                 │
         PC               Mobile
       活跃时              休眠
```

或者：

```text
                Zhaoxi
                   │
          Active Presence
                   │
          ┌────────┴────────┐
          │                 │
         PC               Mobile
        休眠               活跃
```

目标体验：

> 朝汐有时候待在电脑里。  
> 有时候跑到手机里。  
> 但始终只有一个朝汐。

---

# 三、阶段一：Presence 基础

优先强化朝汐在电脑环境中的存在感。

## 1. 桌宠状态

为 PC 端增加桌宠形态。

桌宠不是单纯的装饰，而是朝汐在电脑上的主要 Presence 表现方式之一。

可能包含：

- 桌面常驻
- 空闲状态
- 工作状态
- 铁幕陪伴状态
- Tool 调用状态
- 思考状态
- 简单表情变化
- 简单动作
- 呼出聊天窗口
- Life HUD 状态提示

例如：

```text
正常使用电脑
    ↓
朝汐桌面待机

开始铁幕
    ↓
朝汐进入陪伴 / 工作状态

调用 Tool
    ↓
表现为正在执行任务

长时间无人操作
    ↓
进入休息状态
```

---

## 2. Presence 状态机

逐步建立统一状态：

```text
Idle
Working
Thinking
UsingTool
Sleeping
Away
Handoff
```

桌宠、手机端、通知系统等都读取同一个 Presence 状态，而不是各自实现独立逻辑。

---

# 四、阶段二：手机端

开发真正适合移动环境的 Zhaoxi 客户端。

手机端不是 PC 端界面的缩小版本。

主要承担：

- 快速聊天
- 快速记录
- 上传照片
- 创建 LifeEvent
- 查看 Life HUD 状态
- 查看任务
- 简单 Tool 操作
- 接收通知
- 外出状态下与朝汐交互

手机端更强调：

> 随时可触达。

而 PC 端更强调：

> 长时间陪伴与工作协作。

---

# 五、阶段三：单实例双端迁移

双端完成后，重点不是普通同步，而是实现：

> **Presence Handoff**

即朝汐在不同设备之间迁移。

例如：

```text
朝汐当前在 PC
      ↓
暗苟酱打开手机
      ↓
手机显示：
“朝汐现在在电脑那边”
      ↓
点击“叫她过来”
      ↓
PC 保存状态
      ↓
PC 释放 Presence
      ↓
Mobile 获取 Presence
      ↓
朝汐出现在手机端
```

回到电脑时则反向执行。

---

## 非活跃设备

非活跃设备不需要完全失效。

仍然可以：

- 查看数据
- 查看历史记录
- 查看朝汐当前所在设备
- 接收普通通知
- 发起 Presence 接管

但不能：

- 开启第二个朝汐实例
- 独立执行 Agent 推理
- 独立执行复杂 Tool
- 同时修改朝汐核心状态

---

# 六、阶段四：统一状态与数据同步

双端共享统一的数据与服务层。

需要同步：

- 对话记录
- 朝汐记忆
- Agent 状态
- Presence
- Tool 状态
- Life HUD 上下文
- 用户配置
- 当前任务
- 当前会话
- 必要缓存

原则：

```text
Mobile
   ↕
Unified Backend
   ↕
PC
```

不是：

```text
PC Data ←→ Mobile Data
```

即服务端 / 统一数据层是真正的数据源，而客户端只是载体。

---

# 七、阶段五：Tool 能力扩展

朝汐后续最重要的能力增强方向之一。

目标：

> 从“回答问题”逐渐走向“完成任务”。

基本结构：

```text
暗苟酱
   ↓
自然语言任务
   ↓
Zhaoxi
   ↓
判断需要哪些 Tools
   ↓
执行
   ↓
检查结果
   ↓
返回完成情况
```

---

# 八、Meme Vault Tool

朝汐未来应能够直接操作 Meme Vault。

例如：

> “把这些图片整理进去。”

朝汐自动完成：

```text
接收图片
   ↓
识别任务
   ↓
调用 Meme Vault Tool
   ↓
导入
   ↓
去重
   ↓
标签 / 分类
   ↓
返回结果
```

用户不需要再：

```text
打开 Meme Vault
→ 找导入按钮
→ 选择图片
→ 填信息
→ 整理
```

朝汐成为 Meme Vault 的自然语言入口。

---

# 九、Life HUD Tool

继续增强已经存在的 Life HUD 联动。

未来可以完成：

- 创建 LifeEvent
- 新建任务
- 修改任务
- 写入铁幕记录
- 写入生活记录
- 添加照片
- 添加地点
- 查询周报
- 查询月报
- 查询睡眠
- 查询运动
- 查询音乐
- 查询番剧
- 关联「记忆的场所」

例如：

> “把刚才骑车的事情记一下。”

朝汐可以直接完成：

```text
理解描述
   ↓
提取时间 / 地点 / 距离
   ↓
创建 LifeEvent
   ↓
关联运动记录
   ↓
关联照片
   ↓
写入 Life HUD
```

---

# 十、通用 Tool 生态

未来朝汐主体应尽量保持稳定。

新增能力优先通过 Tool 扩展。

```text
Zhaoxi Core
│
├── Life HUD Tool
├── Meme Vault Tool
├── File Tool
├── Image Tool
├── Browser Tool
├── Search Tool
├── Calendar Tool
├── Notification Tool
├── System Tool
└── Future Tools
```

Zhaoxi Core 负责：

- 理解任务
- 规划
- Tool 选择
- Tool 调用
- 多 Tool 协作
- 错误恢复
- 结果整合
- 用户交互

具体业务逻辑交给对应 Tool。

---

# 十一、阶段六：多 Tool 协作

当 Tool 数量增加后，让朝汐能够组合执行任务。

例如：

> “把今天骑车的照片整理一下，然后记进 Life HUD。”

可能执行：

```text
图片 Tool
   ↓
读取照片信息
   ↓
File Tool
   ↓
整理文件
   ↓
Life HUD Tool
   ↓
创建 LifeEvent
   ↓
写入地点 / 运动 / 照片
```

又例如：

> “把这批 Meme 处理一下。”

可能执行：

```text
File Tool
   ↓
Image Tool
   ↓
Meme Vault Tool
   ↓
完成
```

长期目标是让暗苟酱不用思考：

> “这件事应该打开哪个软件？”

只需要直接告诉朝汐。

---

# 十二、阶段七：适度主动性

生活 Agent 如果永远等待指令，仍然更像工具。

未来可以增加有限主动能力。

例如发现：

- 铁幕结束后未总结
- 某项长期目标很久没有推进
- Life HUD 出现值得关注的趋势
- 某批文件尚未整理
- 某个重要事件即将发生

朝汐可以主动做出轻量提示。

但主动性必须受到严格约束。

---

## 打扰等级

可以建立类似：

```text
Level 0
不主动提示

Level 1
桌宠轻量表现

Level 2
一句轻提醒

Level 3
普通通知

Level 4
重要主动提醒
```

核心原则：

> **Presence 不等于不断说话。**

有时候朝汐安静地待在那里，比频繁刷存在感更像真正长期陪伴的 Agent。

---

# 十三、Tool 权限系统

当朝汐逐渐获得真实行动能力后，需要明确权限边界。

例如：

```text
读取 Life HUD
→ 自动允许

创建普通 LifeEvent
→ 自动允许

整理 Meme Vault 图片
→ 自动允许

删除大量文件
→ 需要确认

覆盖重要记录
→ 需要确认

发送外部消息
→ 需要确认

高风险系统操作
→ 必须确认
```

目的不是限制朝汐，而是让她能够安全地获得越来越大的行动能力。

---

# 十四、阶段八：语音交互

未来可以增加语音能力。

但定位不是语音恋爱游戏，而是自然的人机交互入口。

例如：

> “朝汐，把刚才骑车那段记一下。”

或者：

> “帮我看看今天还有什么没做。”

语音特别适合：

- 外出
- 躺着
- 做饭
- 整理东西
- 不方便打字
- 手机环境

它可以成为手机端尤其重要的交互方式。

---

# 十五、视觉方向原则

不把朝汐做成 GalGame。

不以以下形式作为主要方向：

- 传统 Gal 对话框
- 半身立绘占据主要 UI
- 好感度系统
- 恋爱养成玩法
- 剧情选择树
- 房间养成
- 角色收集式设计

因为朝汐的目标不是：

> 让暗苟酱进入朝汐的虚拟世界。

而是：

> **让朝汐逐渐进入暗苟酱真实生活的环境。**

---

# 十六、Live2D 的定位

Live2D 不是必须开发的独立模块。

如果未来使用，只把它视为：

> 桌宠动画实现方案之一。

而不是朝汐的核心交互模式。

优先级低于：

- Presence
- 双端迁移
- Tool 能力
- 数据一致性
- 主动性
- 实际行动能力

如果简单动画已经能够提供足够好的桌宠体验，就没有必要为了 Live2D 本身而增加复杂度。

# 十九、长期产品原则

### 1. 朝汐只有一个

设备只是她暂时待着的地方。

### 2. 不制造第二个朝汐

多端意味着迁移，而不是复制。

### 3. 不为了功能数量而开发

优先解决真实使用中出现的问题。

### 4. 不把朝汐做成 GalGame

她是 Agent，不是恋爱模拟角色。

### 5. 不要求用户进入朝汐的世界

让朝汐进入用户已经存在的生活环境。

### 6. 能行动比会说更多话重要

新能力优先考虑是否能真正减少操作成本。

### 7. Tool 优先于核心膨胀

新增业务能力尽量通过 Tool 扩展。

### 8. 主动但不烦

长期存在必须伴随克制。

### 9. Presence 是体验的一部分

桌宠、状态迁移、设备切换都不只是 UI，而是朝汐“只有一个”的体现。

### 10. 从真实使用中继续生长

当前没有必要提前构想几十个模块。

未来真正缺少什么，应由长期使用中的需求自然暴露。

---

# 二十、一句话路线

> **让朝汐从一个能够聊天和调用工具的 Agent，逐渐变成只有一个实例、能够在电脑与手机之间迁移、长期存在于生活环境中，并能通过各种 Tools 实际替暗苟酱完成事情的个人生活 Agent。**
